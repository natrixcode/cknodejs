# SQL-міграції PostgreSQL

Міграції — це послідовні зміни структури або даних БД. Команда
`npm run db:migrate` застосовує SQL із `database/migrations/` через `pg`.
Старт API (`npm start`, `npm run dev`, стандартний запуск контейнера `server`)
**не запускає міграції автоматично**.

## Як створити міграцію

1. Оновіть гілку та перевірте номери в `database/migrations/`.
2. Створіть файл із наступним вільним номером, більшим за наявні:
   `0001_description.sql`, `0002_description.sql` тощо.
3. Використовуйте рівно чотири цифри `0001`–`9999`, підкреслення та опис
   малими латинськими літерами, цифрами й підкресленнями; опис починається
   з літери. Наприклад, `0003_update_calculation_function.sql`.
4. Запишіть звичайний SQL у UTF-8 із закінченнями рядків LF. Правило
   `.gitattributes` зберігає LF для міграцій і на Windows.
5. Перевірте міграцію на своїй тестовій БД, потім передайте файл на рев'ю.

Файли виконуються за числовим номером, пропуски між номерами дозволені.
Однакові номери навіть із різними описами спричиняють помилку до підключення
до БД. Узгоджуйте номери між учасниками до застосування спільних змін.
`.gitkeep` ігнорується. Інші файли з неправильними назвами та вкладені
каталоги відхиляються, щоб SQL не був випадково пропущений.

Кожен файл передається PostgreSQL **цілком**, без розбиття за `;`.
Підтримуються кілька SQL-команд, обмеження, функції з тілами `$$…$$`
або `$body$…$body$`, тригери й блоки `DO`.

**Не пишіть власні `BEGIN`, `COMMIT`, `ROLLBACK` або інші команди керування
транзакцією на верхньому рівні міграції.** Транзакцію створює виконавець;
ручний `COMMIT` порушує гарантію атомарності. `BEGIN … END` усередині тіла
PL/pgSQL-функції — частина мови функції, його використовувати можна.
Операції, несумісні з транзакціями, наприклад `CREATE INDEX CONCURRENTLY`,
`VACUUM` і `CREATE DATABASE`, поки не підтримуються. Команди клієнта `psql`,
зокрема `\i`, також не підтримуються.

## Запуск через Docker

Виконуйте з кореня репозиторію. Потрібні запущений Docker Desktop і наявний
`.env`, створений за головним [README](../README.md).

```sh
docker compose up -d --wait db
docker compose build server
docker compose run --rm --no-deps server npm run db:migrate
```

Це окремий одноразовий контейнер сервісу `server`: команда замінює його
стандартний запуск API й не публікує порт API. `--no-deps` використовує вже
готовий `db`, а `--rm` прибирає лише цей одноразовий контейнер після завершення.
Наявна база та її volume зберігаються. Семантика запуску описана в
[довідці Docker Compose](https://docs.docker.com/reference/cli/docker/compose/run/).

Compose передає ті самі параметри, що й API: `PGHOST=db`, `PGPORT=5432`,
`PGDATABASE`, `PGUSER`, `PGPASSWORD` із `POSTGRES_*` у `.env`.
Пароль не потрібно передавати аргументом команди або виводити в термінал.
Міграції працюють в окремому `Client`, без коротких тайм-аутів SQL-запитів API;
тайм-аут встановлення з'єднання — 3 секунди.

Dockerfile копіює `src/` і `database/migrations/` в образ. Після додавання чи
виправлення **ще не застосованої** міграції повторіть `docker compose build server`
перед запуском: простий перезапуск старого контейнера не оновить SQL-файли.

У PowerShell, якщо `docker` відсутній у `PATH`, можна використати повний шлях
до `docker.exe` через оператор `&`; аргументи Compose залишаються тими самими.

## Локальний запуск без контейнера сервера

Потрібні Node.js 24, встановлені залежності (`npm ci`) і доступний PostgreSQL.
Задайте змінні `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`
у середовищі процесу, потім виконайте:

```sh
npm run db:migrate
```

На Windows за блокування `npm.ps1` використовуйте `npm.cmd run db:migrate`.
Для БД із Compose локальний хост — `127.0.0.1`, порт — `POSTGRES_PORT` із `.env`
(типово `5432`), назва БД й облікові дані відповідають `POSTGRES_*`.
Сам npm-скрипт не читає `.env`: файл Compose містить інші назви змінних.

Альтернатива — записати **PG*** налаштування в приватний `.env.pg` та виконати:

```sh
node --env-file=.env.pg src/database/migrate.js
```

Файли `.env.*` ігноруються Git і Docker. Не додавайте до репозиторію паролі.
За потреби окремої тестової папки є явний параметр:

```sh
npm run db:migrate -- --directory tests/my-migrations
```

Такий запуск також повинен використовувати окрему тестову БД через
`PGDATABASE`. Без параметра шлях завжди визначається від коду проєкту,
а не від поточної робочої папки.

## Історія, транзакції та повторний запуск

Виконавець створює `public.schema_migrations` зі стовпцями:

| Стовпець | Значення |
| --- | --- |
| `number` | Числовий номер міграції, первинний ключ. |
| `filename` | Повна назва SQL-файлу. |
| `checksum` | SHA-256 початкових байтів файлу. |
| `executed_at` | Час запису виконання, `timestamptz`. |

Спочатку перевіряється **вся** виконана історія: чи існує кожен файл,
чи збігаються назва та SHA-256. Якщо виконаний файл змінено, перейменовано
або видалено, нові міграції не запускаються. Це працює і для порожньої папки,
якщо в БД уже є історія. На новій БД порожня папка є успішним запуском:
створюється лише службова таблиця, без бізнес-таблиць.

Перед виконанням будь-якого нового файлу також перевіряється порядок номерів.
Якщо є невиконана міграція з номером, меншим за максимальний уже виконаний,
запуск завершується помилкою `Migration order mismatch`: **жодна нова міграція
не запускається**, історія залишається незмінною. Наприклад, після виконання
`0002` і `0010` додавання `0005` разом із `0011` заблокує обидва нові файли.
Узгодьте для невиконаної міграції новий вільний номер, більший за максимальний
виконаний; виконані файли не перенумеровуйте. Пропуски номерів дозволені,
але заповнювати їх після виконання міграцій із більшими номерами не можна.

Кожен новий файл і запис у `schema_migrations` виконуються в одній транзакції
через одне з'єднання, відповідно до
[вимог node-postgres](https://node-postgres.com/features/transactions).
У разі SQL-помилки виконується `ROLLBACK`, наступні файли не запускаються,
а команда завершується ненульовим кодом. Попередні успішні міграції залишаються
застосованими. Після виправлення невиконаного файлу повторіть ту саму команду:
вже виконані файли будуть пропущені.

Сесійний advisory lock на цьому самому з'єднанні захищає весь запуск,
включно з перевіркою історії й проміжками між транзакціями. Другий процес
одразу завершується з помилкою; повторіть його після завершення першого.
З'єднання закривається в `finally` після успіху або помилки, також обробляються
`SIGINT`/`SIGTERM`. PostgreSQL звільняє сесійні блокування при закритті сесії;
див. [документацію advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS).

**Виконані міграції не редагуємо й не видаляємо**, навіть для виправлення
коментаря або форматування: це змінює контрольну суму. Для зміни структури,
функції чи тригера додаємо новий файл із новим номером. При невідповідності
відновіть точний оригінал із Git. Не обходьте перевірку ручним редагуванням
службової таблиці. Автоматичні зворотні міграції (`down`) не реалізовані.

## Як читати результат і помилки

| Повідомлення | Значення та дія |
| --- | --- |
| `Applied …` | Файл і запис історії закомічено. |
| `Skip …: already applied` | Файл збігається з історією; повторно не виконується. |
| `Migrations complete: 0 applied, …` | Нових міграцій немає; код завершення `0`. |
| `Invalid migration entry` / `Duplicate migration number` | Виправте назву або конфлікт номерів невиконаних файлів. |
| `Cannot read migrations directory` / `Cannot read …` | Перевірте шлях, наявність файлів в образі та права читання. |
| `Migration history mismatch` | Відновіть оригінальний виконаний файл; нові зміни оформіть окремою міграцією. |
| `Migration order mismatch` | Є невиконаний файл із номером нижчим за максимальний виконаний. Жодних нових файлів не виконано; узгодьте новий вільний номер вище максимального виконаного. |
| `Another migration process is running` | Дочекайтеся завершення іншого процесу й повторіть запуск. |
| `Migration … failed [код]` | Вказано файл, код PostgreSQL і, за наявності, позицію символу в SQL. Виправте невиконаний файл. |
| `Migration run failed [код]` | Перевірте доступність PostgreSQL, `PG*` налаштування й права користувача. |
| `ROLLBACK could not be confirmed` | З'єднання могло обірватися; перевірте історію й стан БД перед повтором. |

Приклади SQLSTATE: `42601` — синтаксична помилка, `42P01` — немає таблиці,
`23505` — порушення унікальності, `42501` — недостатньо прав,
`28P01` — помилка автентифікації. `ECONNREFUSED` означає відмову TCP-з'єднання.
Повний перелік — у [довідці PostgreSQL](https://www.postgresql.org/docs/18/errcodes-appendix.html).
SQL, значення даних, повідомлення `RAISE`, конфігурація підключення й пароль
не виводяться в логи виконавця; для діагностики використовуються код і позиція.
Перевірити код завершення можна через `$LASTEXITCODE` у PowerShell або `$?` у sh.

Історію можна переглянути SQL-запитом у DBeaver:

```sql
SELECT number, filename, checksum, executed_at
FROM public.schema_migrations
ORDER BY number;
```

## Решта папок database/

`functions/`, `triggers/`, `schema/` і `seeds/` **самі автоматично не
застосовуються**. Це допоміжні файли для організації SQL. Для їх застосування
потрібні відповідні міграції, які містять потрібний SQL, зокрема
`CREATE OR REPLACE FUNCTION`, `CREATE TRIGGER` або зміни схеми.
Виконавець не підвантажує ці файли динамічно: вміст застосованої міграції
має залишатися відтворюваним незалежно від майбутніх змін допоміжних файлів.

## Перевірки

Файлові перевірки та перевірки CLI без доступної БД:

```sh
npm run check
npm run test:db-migrations
```

Без `MIGRATION_TEST_ADMIN_DB` інтеграційна група явно позначається як пропущена.
Для всіх перевірок на справжньому PostgreSQL виконайте з кореня репозиторію
(PowerShell або sh):

```sh
docker compose up -d --wait db
docker compose build server
docker compose run --rm --no-deps -e MIGRATION_TEST_ADMIN_DB=postgres --volume "${PWD}/tests:/app/tests:ro" server npm run test:db-migrations
```

Обліковий запис має мати право `CREATEDB`. Для кожного сценарію тести створюють
**нову окрему БД** `cknodejs_migration_test_<випадковий суфікс>` та після тесту
видаляють тільки створену ним БД. Наявна прикладна база й Docker volume
не видаляються. SQL для перевірок міститься в `tests/database/migrations.test.js`
та записується в тимчасові папки; `database/migrations/` залишається без тестових файлів.

Перевіряються порожня папка та `.gitkeep`, формат і дублікати номерів,
числовий порядок і блокування нових файлів за наявності невиконаного нижчого
номера, SHA-256 і час виконання, повторний запуск, відкат SQL і
запису історії, збереження попередніх міграцій, зупинка наступних файлів,
зміна/видалення/перейменування виконаного файлу, функція з тригером і
обмеженням, закриття з'єднань та два одночасні процеси CLI.

## Виправлення 0012: доступ до заняття та режим опублікованого дня

Міграція `0012_lesson_access_and_daily_routine.sql` не змінює файли 0001–0011.
`kms_can_manage_lesson` приймає роль користувача `employee` та зберігає сумісність
зі старою роллю `teacher`, дозволеною схемою 0001. Працівник повинен мати посаду
`teacher`, статус `active` і бути викладачем саме цього заняття. Перевірки
`users.status`, `is_active`, права `admin` і `manager` збережені. Це лише
SQL-функція дозволу; авторизація HTTP API тут не реалізована.

`kms_publish_group_day` тепер зберігає переданий початок дня в
`kms_group_day_windows`. Після INSERT/UPDATE/DELETE блоків перевіряються рівно
три прийоми їжі, один сон і межі того самого восьмигодинного вікна.
При перенесенні блоку перевіряються і стара, і нова пара група/дата.
Чинні обмеження тривалості, накладань і послідовних прийомів їжі збережені.
Вісім годин означають вікно, як у 0005, а не вимогу заповнити кожну хвилину.

**Явне рішення для сумісності:** день захищений, доки містить хоча б одне
заняття зі статусом `published` (дата в `Europe/Kyiv`). Дні лише з чернетками
дозволяють поступове заповнення. У 0005 час початку не зберігався, тому 0012
не вгадує його для старих опублікованих днів і не змінює їхні дані.
Перед редагуванням такого дня повторіть `kms_publish_group_day(group_id, day,
correct_day_start)`, інакше буде `KMS_REPUBLISH_DAY_REQUIRED`. Якщо старий режим
уже пошкоджений, спочатку переведіть усі заняття цього дня в `draft`, виправте
блоки й опублікуйте з правильним часом. Пряме встановлення статусу `published`
не замінює функцію публікації; без збереженого вікна редагування блоків теж
вимагатиме повторної публікації.

Коректні зміни часу та багаторядкові UPDATE дозволені. Для заміни блоку
кількома командами можна відкласти перевірку до кінця транзакції:

```sql
BEGIN;
SET CONSTRAINTS trg_kms_published_routine_guard DEFERRED;
-- DELETE старого блоку та INSERT заміни без порушення інших обмежень.
COMMIT; -- неповний або некоректний режим відхилить усю транзакцію
```

Тригер використовує наявне транзакційне advisory-блокування публікації 0005.
Інші бізнес-правила, зарплати й фінансові формули не змінені.

### Інтеграційні тести бізнес-правил

Потрібні PostgreSQL 18, Node.js 24 та обліковий запис із `CREATEDB`.
Задайте `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, а також
`MIGRATION_TEST_ADMIN_DB=postgres` у середовищі процесу, потім виконайте:

```sh
npm run test:db-business-rules
npm test
```

У PowerShell використовуйте `npm.cmd`, якщо `npm.ps1` заблокований.
Альтернатива для наявного Compose-сервісу після збирання образу:

```sh
docker compose run --rm --no-deps -e MIGRATION_TEST_ADMIN_DB=postgres --volume "${PWD}/tests:/app/tests:ro" server npm run test:db-business-rules
```

Тест сам створює випадкові БД `cknodejs_rules_test_<uuid>` і видаляє лише їх;
прикладна БД, її міграції та volume не змінюються. Не задавайте тестову БД
вручну: `PGDATABASE` для дочірнього migration runner замінюється автоматично.
Без `MIGRATION_TEST_ADMIN_DB` SQL-тести явно пропускаються.

Спочатку на оригінальних 0001–0011 тести підтверджують відмову викладачу та
можливість пошкодити вже опублікований режим. Потім перевіряють оновлення до
0012 зі збереженням історії, чисте встановлення всіх міграцій, повторні запуски
та регресії прав і режиму. Для запуску лише відтворення встановіть
`SQL_RULES_REPRO_ONLY=1`; для повної перевірки приберіть цю змінну.
Express для цих тестів не запускається.

### 1. Мета бізнес-аналітичної роботи

### 3. Аналіз результатів QA та відкритих дефектів
Згідно зі звітом QA.md від 28.10.2026, сервер запускається, база даних доступна, health-check маршрути працюють, а основні GET-колекції проходять перевірки. Водночас зафіксовано такі проблеми, що потребують перевірки та доопрацювання:

**3.1. Розрахунок харчування (BA-ISSUE-01)**
Маршрут: `GET /api/v1/food/calculate`
У QA зафіксовано HTTP 500 на перевірених запитах і проблему роботи з req.query у `src/routes/food_routes.js`.
*Очікувана поведінка:*
- правильний розрахунок вартості за погодженим тарифом;
- контроль коректності параметрів;
- контрольована відповідь у разі некоректних даних;
- відсутність необроблених внутрішніх помилок сервера.

**3.2. Розрахунок навчання (BA-ISSUE-02)**
Маршрут: `GET /api/v1/tuition/calculate`
У QA зафіксовано HTTP 500 на перевірених запитах і проблему обробки параметрів у `src/routes/tuition_routes.js`.
*Очікувана поведінка:*
- правильне застосування тарифу;
- коректний розрахунок пільг;
- дотримання погоджених правил річної передоплати;
- можливість перевірити результат на контрольних даних.

**3.3. Розрахунок беззбитковості (BA-ISSUE-03)**
Маршрут: `GET /api/v1/reports/break-even`
QA зафіксував HTTP 501. Повноцінний розрахунок беззбитковості на момент перевірки був недоступний. Необхідно погодити склад доходів і витрат, спосіб розрахунку точки беззбитковості та очікувані результати для різної кількості груп, дітей, працівників і приміщень.

**3.4. Налаштування та формат помилок (BA-ISSUE-04 і BA-ISSUE-05)**
QA зафіксував HTTP 404 для `GET /api/v1/settings` та HTML-відповідь для невідомого маршруту API. Потрібно погодити поведінку системи під час першого запуску й уніфікований JSON-формат помилок.

**3.5. Неповне інтеграційне тестування**
Частину тестів було пропущено через відсутність конфігурації `MIGRATION_TEST_ADMIN_DB`. Необхідно налаштувати тестове середовище, виконати пропущені перевірки та повторно протестувати маршрути після виправлень.
