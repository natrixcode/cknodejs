## Як система визначає роль

| Роль у матриці | Як записано в базі |
|---|---|
| Адміністратор | `users.role = 'admin'`, лише один |
| Менеджер | `users.role = 'manager'` |
| Батьки | `users.role = 'parent'`, звʼязок через `users.parent_id` |
| Вихователь | `users.role = 'employee'`, `employees.position = 'educator'`, `group_staff.role = 'educator'` |
| Помічник | `users.role = 'employee'`, `employees.position = 'assistant'`, `group_staff.role = 'assistant'` |
| Викладач | `users.role = 'employee'`, `employees.position = 'teacher'` (#48 зводить до однієї моделі) |

Вихователь і помічник мають однакову `users.role`. Тому розрізняти їх має SQL, а не middleware (#48).

Працівники без ролі в групі (директор, кухар, медсестра, бухгалтер) до окремого рішення BA доступу до API не мають (#48).

## Загальні правила

1. Користувач бачить лише дані в межах своєї ролі. Перевірка належності запису (своя дитина, своя група, власне заняття) — у SQL-функціях `kms_can_view_*`.
2. Права на дані групи залежать від актуальних призначень у `group_staff`.
3. Помічник не має доступу до API, крім входу (#48).
4. Фізичного видалення дітей, батьків, рахунків і платежів немає.
5. Неописана операція за замовчуванням дозволена лише admin.

## Коди відповідей

| Код | Коли |
|---|---|
| 401 | Користувач не увійшов або токен прострочений |
| 403 | Ролі не дозволено цю дію |
| 404 | Запису не існує |
| 409 | Дія дозволена, але суперечить стану даних (другий admin, переплата, повторна архівація) |
| 422 | Порушено правило розкладу |
| 500 | Не має виникати; кожен такий випадок — дефект (#50) |

## Пропозиції, не погоджені з викладачем

Запропоновано BA, але до погодження не реалізується:

- manager створює й змінює кімнати, предмети, тарифи харчування, працівників;
- manager бачить «операційні» звіти без прибутку;
- працівник бачить власний профіль;
- вихователь бачить контакти батьків своєї групи;
- батьки бачать свої знижки, групу дитини, відвідуваність, доповнюють дані дитини;
- викладач погоджує зміни власного розкладу.
