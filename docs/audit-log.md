# Журнал змін (історія даних)

Вимога замовника: база зберігає історію кожної зміни даних — хто, коли, що змінив, яким було значення до й після.

Актуально на 07.11.2026.

## 1. Що є на main (цикл 4)

Міграція 0011 створила таблицю `kms_audit_log` і тригер `kms_audit_row()`.

| Поле | Що зберігає |
|---|---|
| `table_name` | Таблиця, у якій змінили дані |
| `record_key` | Ключ зміненого запису |
| `operation` | `INSERT`, `UPDATE` або `DELETE` |
| `old_data` | Запис до зміни (JSON) |
| `new_data` | Запис після зміни (JSON) |
| `actor_user_id` | Користувач API, який зробив зміну |
| `database_user` | Користувач PostgreSQL |
| `changed_at` | Час зміни |

Тригер стоїть на 22 таблицях: діти, батьки, звʼязки й родичі, групи, кімнати, працівники, призначення, предмети, розклад, режим дня, тарифи, знижки, рахунки, платежі, зарплати, витрати, параметри зарплат, налаштування.

Доступ: `REVOKE ALL ON kms_audit_log FROM PUBLIC`. Маршруту в API немає — журнал можна прочитати лише напряму в базі.

## 2. Чого бракує (виявлено в циклі 5)

| Прогалина | Наслідок |
|---|---|
| API не передає автора зміни (`kms.actor_user_id`) | У всіх записах `actor_user_id` порожній — невідомо, хто змінив |
| Без аудиту `users`, `food_rates`, `kms_group_day_windows` | Зміни користувачів і частини налаштувань не потрапляють в історію |
| `TRUNCATE` обходить рядкові тригери | Масове очищення таблиці пройде без сліду |
| Журнал не захищений від змін | Власник бази може змінити чи видалити історію |
| Немає перевірки нових таблиць | Нова таблиця без тригера непомітно лишиться без історії |

## 3. Рішення BA (цикл 5, задача #55)

- Історія пишеться для кожної `INSERT`, `UPDATE`, `DELETE` у кожній таблиці з даними, зокрема нових (`attendance` — #53, архів — #52).
- Кожен запис містить автора — користувача API, який зробив зміну.
- Паролі (`users.password_hash`) в історію не потрапляють — маскуються.
- Журнал незмінний: `UPDATE`, `DELETE`, `TRUNCATE` заборонені → `KMS_AUDIT_IMMUTABLE`.
- `TRUNCATE` таблиць з даними заборонений.
- Історія зберігається назавжди.
- Історія структури бази — таблиця `schema_migrations`, окремо не дублюється.
- Тест перевіряє, що кожна таблиця в `public`, крім `kms_audit_log` і `schema_migrations`, має тригер аудиту.

## 4. Права доступу до журналу

| Дія | Admin | Manager | Вихователь | Викладач | Батьки | Помічник |
|---|---|---|---|---|---|---|
| Перегляд історії запису (`GET /history`) | Так | Ні | Ні | Ні | Ні | Ні |
| Стан запису на момент часу (`GET /history/state`) | Так | Ні | Ні | Ні | Ні | Ні |
| Зміна чи видалення історії | Ні | Ні | Ні | Ні | Ні | Ні |

Інші ролі отримують `403`.

## 5. Як перевірити

1. Увійти як admin, змінити дані дитини через API.
2. `GET /history?table=children&id=<id>` — є запис `UPDATE` з `actor_user_id` цього admin, старими й новими даними.
3. Те саме під manager → `403`.
4. Змінити користувача — у `old_data` і `new_data` немає `password_hash`.
5. Спроба `DELETE FROM kms_audit_log` у базі → помилка `KMS_AUDIT_IMMUTABLE`.
