## Правила генерації

- Функція `kms_generate_group_day(group_id, date)` повертає три рядки `schedule`
  у статусі `draft`, кожен тривалістю 30 хвилин.
- Група активна; кімната — `groups.room_id`, доступна або зайнята групою,
  не в ремонті й не неактивна.
- Початок дня береться з `kms_group_day_windows` для цієї групи/дати;
  без запису — `08:00`. Вікно — чинні 8 годин, зона — `Europe/Kyiv`.
- До генерації потрібно створити рівно три прийоми їжі по 30 хвилин і один
  сон на 60 хвилин у `kms_daily_blocks`. Час цих блоків не вигадується.
  Використовується наявна `kms_validate_group_day` і чинні тригери режиму дня.
- Вибрані предмети розташовуються в порядку циклу в найраніші доступні вікна.
  Межі вікон беруться з кінців зайнятих інтервалів: фіксованої сітки по 30
  хвилин немає, тому блок, що закінчився о 09:07, не округлюється до 09:30.
- Викладач має `position='teacher'`, `status='active'` та відповідний запис
  `employee_subjects`. Серед одночасно доступних викладачів обирається найменший ID.
- Зайнятість кімнат і викладачів перевіряється за **draft і published** інших
  груп. Межі інтервалів напіввідкриті: завершення о 10:00 дозволяє початок о 10:00.
- За наявності будь-якого заняття групи, що перетинає цю київську дату,
  генерація відхиляється. Наявні чернетки й публікації не змінюються.
- Генерація атомарна: спочатку складається повний план, потім записуються
  всі три заняття в одній SQL-команді. Навіть помилка тригера на третьому
  INSERT відкочує попередні INSERT та їхній аудит.
- Спільне транзакційне advisory-блокування `(2026, 1005)` серіалізує генерацію
  з іншими генераціями та наявними захищеними операціями розкладу/режиму дня.
  Використовується стандартний для застосунку рівень ізоляції READ COMMITTED.

### Календарне чергування

Усі предмети впорядковуються за ID. Для `N` предметів і календарної різниці
`d = date - 2026-01-01` початковий індекс із нуля:

```text
offset = ((d × 3) % N + N) % N
indices = offset, (offset + 1) % N, (offset + 2) % N
```

За `N < 3` — помилка 422. Наприклад, для A, B, C, D, E:
31.12.2025 → C D E; 01.01.2026 → A B C; 02.01.2026 → D E A;
04.01.2026 → E A B. Пропущені дати також враховуються. Для рівно трьох
предметів трійка щодня однакова — це наслідок погодженої формули.

Дати можна генерувати в будь-якому порядку. Видалення й ручне редагування
іншого дня не змінюють вибір предметів. Окрема історія виділення предметів
і заборона генерації попередніх дат не додаються. Якщо для обраної трійки
немає потрібних викладачів/часу, предмети не підміняються іншими.

**Обмеження:** зміна переліку предметів може змінити результат майбутньої
генерації, включно з повторною генерацією видаленого дня. Наявні розклади
автоматично не перебудовуються. Час і викладачі також залежать від поточної
зайнятості; календарна незалежність стосується вибору предметів.

## API

`POST /api/v1/schedule/generate`, ролі **admin, manager**:

```json
{"group_id": 1, "date": "2026-11-12"}
```

`group_id` — додатне безпечне ціле число JSON; `date` — реальна дата
`YYYY-MM-DD` від 0001 року. Зайві поля відхиляються. Успіх — **201**:
`{"status":"success","data":[…три заняття…]}`. Без входу — 401,
інші ролі — 403, некоректне тіло — 400, бізнес-помилки — 422.

Публікація залишається ручною: `POST /api/v1/schedule/publish`, лише **admin**,
з усіма трьома `schedule_ids`. Для нестандартного початку дня передайте той
самий `day_start`, що використано генерацією. Manager отримує 403.

### Збережений контракт /validate

`POST /api/v1/schedule/validate` збережено для admin/manager. Він перевіряє
**один запропонований інтервал**, а не генерує чи публікує день:

```json
{
  "group_id": 1,
  "teacher_id": 2,
  "room_id": 1,
  "start_time": "2026-11-12T09:00:00+02:00",
  "end_time": "2026-11-12T09:30:00+02:00",
  "exclude_id": "123",
  "subject_id": 3
}
```

`exclude_id` необов'язковий: виключає з перевірки накладань лише наявну
чернетку цієї групи. `subject_id` — нове необов'язкове поле; якщо воно не
передане, але є `exclude_id`, предмет береться з чернетки. Без обох полів
перевіряється інтервал і активність викладача, але не його предмет.

SQL перевіряє активність групи/викладача, кімнату, готовність режиму дня,
межі дня та накладання; використовує спільну з генерацією функцію
`kms_schedule_interval_conflict`. На відміну від генерації, ручний інтервал
не обмежується 30 хвилинами. Успіх — 200,
`{"status":"success","data":{"valid":true}}`. Записів не створює.
Це перевірка поточного стану, а не резервування часу: під час публікації
чинні SQL-обмеження перевіряються знову. Контракт варто звірити з виконавцем #50;
маршрут не видалено.

### Бізнес-помилки (422)

| Код | Причина |
| --- | --- |
| `KMS_GENERATION_DAY_EXISTS` | Цього дня вже є чернетка або опубліковане заняття. |
| `KMS_GENERATION_INSUFFICIENT_SUBJECTS` | Менше трьох предметів. |
| `KMS_GENERATION_NO_AVAILABLE_TEACHER` | Для вибраного предмета немає активного кваліфікованого вільного викладача. |
| `KMS_GENERATION_NO_FREE_WINDOW` | Не залишилося часу для повної послідовності занять. |
| `KMS_GENERATION_ROOM_CONFLICT` | Доступні вікна зайняті в кімнаті іншими заняттями. |
| `KMS_GENERATION_INVALID_PARAMETERS` | Некоректні параметри прямого SQL-виклику. |
| `KMS_SCHEDULE_GROUP_CONFLICT` / `KMS_SCHEDULE_ROOM_CONFLICT` / `KMS_SCHEDULE_TEACHER_CONFLICT` | Накладання під час перевірки інтервалу. |
| `KMS_SCHEDULE_ROOM_UNAVAILABLE` | Кімната не існує або недоступна. |
| `KMS_SCHEDULE_INVALID_INTERVAL` / `KMS_SCHEDULE_INVALID_EXCLUDE` | Некоректний інтервал або виключена чернетка. |

Також використовуються наявні `KMS_GROUP_NOT_ACTIVE`,
`KMS_DAILY_ROUTINE_INCOMPLETE`, `KMS_BLOCK_OUTSIDE_WORKDAY`,
`KMS_LESSON_OUTSIDE_WORKDAY`, `KMS_LESSON_DAILY_BLOCK_CONFLICT`,
`KMS_TEACHER_SUBJECT_MISMATCH`. Формат помилки — `{"message":"KMS_…"}`.

## Демо через Bruno

Після інтеграції актуального main та узгодження номера застосуйте міграції
звичайною командою проєкту, потім перебудуйте API:

```sh
docker compose build server
docker compose run --rm --no-deps server npm run db:migrate
docker compose up -d --no-deps server
```

1. Відкрийте наявну колекцію `bruno/opencollection.yml`.
2. Підготуйте активну групу з кімнатою, щонайменше три предмети й активних
   викладачів з `employee_subjects`. Для демонстрації чергування краще п'ять
   предметів. На обрану дату ще не повинно бути занять цієї групи.
3. Запитами `Manual Schedule / Create meal` і `Create nap` створіть блоки на
   ту саму дату: 08:00–08:30, 12:00–12:30, 15:00–15:30 та сон 13:00–14:00.
   Для листопада використовуються часові позначки з `+02:00`.
4. Увійдіть через `POST /api/v1/auth/login` як manager. Збережіть отриманий
   токен лише в локальній/секретній змінній Bruno `token`, без коміту.
5. Задайте локальні змінні `group_id` (число) і `schedule_date` (`YYYY-MM-DD`).
   Виконайте `Manual Schedule / Generate day`: очікуйте 201 і три `draft`.
6. Перегляньте їх через `GET /api/v1/schedule/{id}` із токеном manager.
7. У `Manual Schedule / Publish day` передайте всі три ID з відповіді генерації.
   З токеном manager очікуйте 403; після входу admin і заміни локального
   `token` — 200, `published: 3`. Повторний GET покаже `published`.
8. Повторіть генерацію цієї групи/дати: 422 `KMS_GENERATION_DAY_EXISTS`.
   Для іншого дня спочатку створіть його блоки; змінюйте лише `schedule_date`.

Постійних паролів чи токенів у запиті та документації немає.

```powershell

npm.cmd test -- --test-concurrency=1
npm.cmd run check
```

Для наявного `.env` Compose параметри можна передати без виведення пароля:

```powershell
node --env-file=.env --input-type=module -e "import { spawnSync } from 'node:child_process'; const r = spawnSync(process.execPath, ['--test', '--test-concurrency=1'], { env: { ...process.env, PGHOST: '127.0.0.1', PGPORT: process.env.POSTGRES_PORT ?? `supertest` для повного HTTP-набору потрібно встановити в окремому тестовому
```
середовищі. Локальний запуск вище використовує devDependencies із `npm ci`.
