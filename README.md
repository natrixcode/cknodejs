## Початкове середовище проєкту

Це технічна основа: JavaScript, Node.js, Express і PostgreSQL через бібліотеку
`pg`, без TypeScript та ORM. Кожен учасник запускає власну локальну базу.
Бізнес-логіка садочка надалі реалізовуватиметься в SQL; зараз немає таблиць
садочка, бізнес-правил, авторизації чи фронтенду.

Встановіть Git, VS Code, Docker Desktop, DBeaver і Bruno за отриманою раніше
інструкцією. Для запуску через Docker встановлювати Node.js або PostgreSQL на
комп'ютер окремо не потрібно. Запустіть Docker Desktop і дочекайтеся готовності
Docker Engine. На Windows використовуйте Linux containers (WSL 2), на macOS —
звичайний Docker Desktop. Команди виконуйте в терміналі з кореня репозиторію.

### Створення .env

Зробіть це один раз, якщо `.env` ще немає. Наявний файл не перезаписуйте.

Windows PowerShell:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

macOS (Terminal):

```sh
if [ ! -f .env ]; then cp .env.example .env; fi
```

Типові значення: база `kindergarten_local`, користувач `student`, пароль
`local_test_only_change_me`, порт сервера `3000`, порт бази на комп'ютері `5432`.
Це лише тестові локальні облікові дані. Compose читає `.env` і передає параметри
контейнерам; `.env` не копіюється в образ. Не додавайте власний `.env` у Git.

### Запуск, стан, логи та зупинка

Перший запуск і запуск після оновлення залежностей:

```sh
docker compose up -d --build --wait
```

Перший запуск завантажить образи й встановить залежності всередині образу
сервера через `npm ci`. Compose почекає, доки `pg_isready` підтвердить готовність
PostgreSQL, і лише тоді запустить сервер. Детальніше про цей порядок — у
[документації Docker Compose](https://docs.docker.com/compose/how-tos/startup-order/).

Стан контейнерів та логи:

```sh
docker compose ps
docker compose logs --tail=100
docker compose logs -f server db
```

Для бази очікуйте `healthy`, для сервера — `Up`. `Ctrl+C` під час перегляду логів
лише завершує їх перегляд.

Звичайна зупинка та повторний запуск тих самих контейнерів:

```sh
docker compose stop
docker compose up -d --wait
```

Зупинка з видаленням контейнерів і мережі, зі збереженням даних:

```sh
docker compose down
```

Node.js отримує SIGTERM, припиняє приймати HTTP-запити, чекає завершення поточних
запитів та викликає `pool.end()` для закриття підключень до бази. Сервер має до
10 секунд на завершення; Compose дає йому 15 секунд.

### Тестові маршрути

За типових налаштувань:

| Метод і адреса | HTTP | JSON |
| --- | --- | --- |
| `GET http://localhost:3000/health` | `200` | `{"status":"ok"}` |
| `GET http://localhost:3000/health/db` | `200` | `{"status":"ok","database":"ok"}` |
| `GET http://localhost:3000/health/db`, коли база недоступна | `503` | `{"status":"error","database":"unavailable"}` |

`/health` перевіряє лише відповідь сервера. `/health/db` виконує `SELECT 1` через
`Pool`. За недоступної бази відповідь не містить пароля, SQL-подробиць або stack
trace; очікування підключення та запиту обмежене тайм-аутами.

Швидка перевірка в PowerShell:

```powershell
Invoke-RestMethod http://localhost:3000/health
Invoke-RestMethod http://localhost:3000/health/db
```

У macOS:

```sh
curl -i http://localhost:3000/health
curl -i http://localhost:3000/health/db
```

Для перевірки сценарію недоступності виконайте `docker compose stop db`:
`/health` має й далі відповідати `200`, а `/health/db` — `503`. Після цього
відновіть базу командою `docker compose up -d --wait db` і повторіть запит до
`/health/db`: очікуйте `200` без перезапуску сервера.

### Перевірка через Bruno

1. Після клонування репозиторію створіть `.env` і запустіть Docker Compose за
   інструкцією вище.
2. У Bruno виберіть **Open Collection** і відкрийте папку **`bruno`** в корені
   клонованого репозиторію. Вона містить `opencollection.yml`; відкриється готова
   колекція `cknodejs`.
3. Відкрийте збережений запит **Server health**: метод `GET`, URL
   `http://localhost:3000/health`. Натисніть Send і перевірте HTTP `200` та
   `{"status":"ok"}`.
4. Відкрийте збережений запит **Database health**: метод `GET`, URL
   `http://localhost:3000/health/db`. Перевірте HTTP `200` та
   `{"status":"ok","database":"ok"}`.
5. Після `docker compose stop db` повторіть обидва запити: `Server health` —
   `200`, `Database health` — `503` із відповіддю з таблиці вище. Поверніть базу командою
   `docker compose up -d --wait db`.

### Підключення через DBeaver

Створіть New Database Connection → PostgreSQL. За незміненого `.env` заповніть:

| Поле | Значення |
| --- | --- |
| Connect by | Host |
| Host | `localhost` |
| Port | `5432` |
| Database | `kindergarten_local` |
| Authentication | Username/password (назва може відрізнятися залежно від версії DBeaver) |
| Username | `student` |
| Password | `local_test_only_change_me` |
| SSL | Вимкнено для цієї локальної навчальної бази |
| SSH tunnel | Вимкнено |

Якщо змінювали `.env`, використайте відповідні `POSTGRES_PORT`, `POSTGRES_DB`,
`POSTGRES_USER`, `POSTGRES_PASSWORD`. Натисніть Test Connection; за першого
підключення дозвольте DBeaver завантажити JDBC-драйвер PostgreSQL. У SQL Editor
виконайте `SELECT 1;` — очікуйте один рядок зі значенням `1`.

У мережі Docker сервер підключається до **`db:5432`**: `db` — назва сервісу в
Compose, яка працює як ім'я хоста. `localhost` усередині контейнера сервера
означає сам контейнер сервера. DBeaver працює на вашому комп'ютері, тому
підключається до **`localhost:5432`** через опублікований порт. Обидва порти
опубліковано лише на `127.0.0.1`, тож доступ призначений для вашого комп'ютера.

### Збереження даних

Дані PostgreSQL зберігаються в іменованому volume `postgres_data`, змонтованому
в `/var/lib/postgresql` (шлях для офіційного образу PostgreSQL 18). Реальна назва
volume має префікс Compose-проєкту, зазвичай `cknodejs_postgres_data`.
Кожен учасник має окремий volume у власному Docker Desktop.

`docker compose stop`, `docker compose down` та перебудова сервера зберігають
volume. Наступний запуск із того самого каталогу використовує ті самі дані.
Інша назва каталогу або `docker compose -p ...` можуть обрати інший volume.

**`docker compose down -v` видаляє volume й усі дані в ньому.** Не використовуйте
цю команду, якщо потрібно зберегти дані. Зміна `POSTGRES_DB`, `POSTGRES_USER` або
`POSTGRES_PASSWORD` у `.env` не перестворює базу й не змінює облікові дані в уже
ініціалізованому volume. Початкові значення застосовуються лише до порожнього
volume; для наявної бази зміни потрібно виконувати окремо в PostgreSQL.

### Як застосовувати зміни коду

Змініть `src/server.js` або `src/db.js`, збережіть файл і виконайте:

```sh
docker compose up -d --build --no-deps server
```

Команда перебудує та перестворить лише сервер. База й дані збережуться. Простий
режим запуску не монтує вихідний код у контейнер, тому саме збереження файлу чи
`docker compose restart server` не застосує зміни коду з комп'ютера.

Перевірка синтаксису в контейнері:

```sh
docker compose exec server npm run check
```

`npm start` запускає сервер, `npm run dev` запускає Node.js у режимі `--watch`,
`npm run check` перевіряє синтаксис обох JavaScript-файлів. Вони доступні в образі;
для звичайної розробки достатньо перебудови вище. Якщо змінюєте залежності та
маєте локальний Node.js 24, оновіть `package.json` і `package-lock.json` через
`npm install` (у PowerShell за блокування `npm.ps1` використайте
`npm.cmd install`), після чого перебудуйте образ.

### Якщо порт зайнятий або запуск не вдався

Якщо Docker повідомляє `port is already allocated` чи `address already in use`,
змініть у `.env` лише порти вашого комп'ютера, наприклад:

```dotenv
SERVER_PORT=3001
POSTGRES_PORT=5433
```

Після цього виконайте `docker compose up -d --wait`. Для маршрутів і Bruno
використовуйте `http://localhost:3001`, у DBeaver — порт `5433`. Усередині Docker
сервер і база й далі використовують `3000` та `db:5432` відповідно.

Якщо не вдається підключитися до Docker Engine, запустіть Docker Desktop і
дочекайтеся його готовності. Перевірте `docker compose ps` та
`docker compose logs --tail=100`. Якщо база готова, але `/health/db` повертає
`503`, перевірте відповідність `.env` обліковим даним наявного volume; не
видаляйте volume для виправлення налаштувань.

# Kindergarten Management System — Requirements

## 1. Загальна інформація

### 1.1. Опис проєкту

**Kindergarten Management System** — серверна інформаційна система для управління приватним дитячим садком.

Система призначена для автоматизації обліку дітей, батьків, працівників, груп, приміщень, навчальних занять, розкладу, харчування, пільг та платежів.

Окремою функцією системи є розрахунок фінансових показників дитячого садочка, прогнозування прибутку та визначення економічно вигідної організації груп.

### 1.2. Мета проєкту

Розробити серверний застосунок, який дозволить:

- централізовано зберігати інформацію про діяльність садочка;
- керувати дітьми, батьками, групами та працівниками;
- організовувати навчальні заняття та розклад;
- автоматично розраховувати вартість навчання та харчування;
- застосовувати пільги та знижки;
- вести облік платежів;
- контролювати використання приміщень;
- розраховувати доходи, витрати та прибуток;
- визначати найбільш вигідний розподіл дітей між групами.

### 1.3. Межі проєкту

Розробляється виключно серверна частина системи. Взаємодія із системою здійснюється через API. Розробка frontend та мобільного застосунку не передбачається.

## 2. Ролі користувачів

### 2.1. Адміністратор (Admin)

Адміністратор є власником дитячого садочка та має повний доступ до системи.

Можливості адміністратора:

- виконання CRUD-операцій над усіма основними сутностями;
- реєстрація дітей та батьків;
- створення груп та розподіл дітей;
- керування працівниками;
- призначення вихователів, помічників та викладачів;
- керування приміщеннями;
- створення та редагування занять;
- формування та коригування розкладу;
- призначення пільг;
- зміна вартості навчання та харчування;
- зміна заробітних плат;
- перегляд історії платежів;
- отримання фінансових звітів;
- розрахунок прибутку;
- прогнозування прибутку для заданої кількості дітей.

### 2.2. Менеджер (Manager)

Менеджер виконує адміністративні функції з обмеженими правами доступу.

Можливості менеджера:

- реєстрація дітей;
- додавання та редагування інформації про дітей і батьків;
- створення та редагування груп;
- призначення дітей до груп;
- перегляд інформації про працівників;
- робота з розкладом у межах наданих прав;
- виконання інших дозволених адміністративних операцій.

Менеджер не має повного доступу до управління фінансовими налаштуваннями та правами адміністратора.

Базова заробітна плата менеджера становить 80 000 грн на місяць.

### 2.3. Батьки (Parent)

Батьки мають доступ виключно до інформації про власних дітей.

Можливості батьків:

- перегляд інформації про власних дітей;
- доповнення інформації про дитину;
- зазначення харчових уподобань;
- перегляд групи дитини;
- перегляд розкладу;
- перегляд вартості навчання;
- перегляд призначеної пільги;
- перегляд кінцевої суми до оплати.

Батьки не можуть переглядати персональні дані, платежі та пільги чужих дітей.

Одна сім'я може мати декількох дітей у садочку.

### 2.4. Викладач (Teacher)

Викладач проводить заняття з окремої дисципліни.

Можливості викладача:

- перегляд власного розкладу;
- перегляд призначених занять;
- перегляд груп, у яких проводяться заняття;
- коригування розкладу в межах наданих прав.

Один викладач не може одночасно проводити заняття для двох груп.

### 2.5. Вихователь (Educator)

Вихователь закріплюється за конкретною групою дітей.

Основні функції:

- робота з призначеною групою;
- перегляд розкладу групи;
- доступ до необхідної інформації про дітей.

Один вихователь закріплюється за однією групою.

### 2.6. Помічник вихователя (Assistant)

Помічник вихователя закріплюється за конкретною групою. Для кожної групи передбачається один помічник вихователя незалежно від кількості дітей.

Система повинна передбачати зберігання інформації про такі сутності:

| User | Обліковий запис користувача |
| Child | Інформація про дитину |
| Parent | Інформація про батьків |
| Relative | Інформація про родичів дитини |
| Group | Група дітей одного віку |
| Employee | Інформація про працівника |
| Educator | Вихователь групи |
| Assistant | Помічник вихователя |
| Teacher | Викладач дисципліни |
| Subject | Навчальна дисципліна |
| Lesson | Конкретне заняття |
| Schedule | Розклад занять |
| Room | Приміщення садочка |
| Discount | Пільга на навчання |
| Meal | Вартість та параметри харчування |
| Payment | Інформація про оплату |
| FinancialSettings | Фінансові параметри |
| ChangeHistory | Історія змін даних |

Додаткові сутності, рекомендовані для чіткого розмежування відповідальності:

| Сутність | Призначення |
|---|---|
| Role / Permission | Ролі та дозволені дії |
| ScheduleItem | Окремий запис розкладу: час, група, дисципліна, викладач, кімната |
| Invoice | Рахунок із зафіксованими сумами та тарифами на момент нарахування |
| Payment | Фактична оплата, що може покривати один або декілька рахунків |
| TuitionPlan / MealRate | Налаштовувані тарифи навчання та харчування з періодом чинності |
| Expense | Фактичні витрати для фінансових звітів |
| AuditLog | Журнал змін основних записів |

**User** містить дані для входу та ролі доступу; **Parent** і **Employee** — бізнес-дані про відповідних осіб. Працівник може мати обліковий запис, але обліковий запис не повинен замінювати картку працівника.

Перелік сутностей є логічною моделлю предметної області. Під час проєктування бази даних окремі сутності можуть бути об'єднані або реалізовані через зв'язки між таблицями.

## 4. Функціональні вимоги

### FR-01. Керування користувачами

Система повинна забезпечувати:

- створення облікових записів;
- автентифікацію користувачів;
- призначення ролей;
- перевірку прав доступу;
- зміну інформації облікового запису;
- блокування несанкціонованого доступу.

### FR-02. Керування дітьми

Адміністратор та менеджер повинні мати можливість:

- створювати записи про дітей;
- переглядати інформацію;
- редагувати записи;
- видаляти записи;
- призначати дитину до групи;
- змінювати групу дитини.

Основна інформація про дитину:

- ідентифікатор;
- ім'я та прізвище;
- дата народження;
- вік;
- батьки;
- група;
- харчові вподобання;
- додаткова інформація;
- призначена пільга.

Вік дитини повинен відповідати встановленим обмеженням.

### FR-03. Керування батьками

Система повинна підтримувати:

- створення запису про батьків;
- перегляд інформації;
- редагування інформації;
- видалення запису;
- прив'язку батьків до дітей.

Один із батьків може бути пов'язаний із декількома дітьми. Одна дитина може мати декількох законних представників.

### FR-04. Керування родичами

Система повинна дозволяти зберігати додаткову інформацію про родичів дитини.

Інформація може включати:

- ім'я родича;
- тип родинного зв'язку;
- посаду або статус;
- додаткові відомості.

Інформація про родичів може використовуватися адміністратором під час прийняття рішення про призначення пільги.

### FR-05. Керування групами

Система повинна підтримувати:

- створення групи;
- перегляд групи;
- редагування групи;
- видалення групи;
- додавання дітей;
- виключення дітей із групи;
- призначення вихователя;
- призначення помічника;
- закріплення приміщення.

Обмеження:

- вік дітей у межах однієї групи повинен бути однаковим;
- максимальна кількість дітей у групі — 20;
- кожна група повинна мати окреме основне приміщення;
- кожна група повинна мати одного вихователя та одного помічника.

### FR-06. Керування працівниками

Адміністратор повинен мати можливість:

- додавати працівників;
- переглядати інформацію;
- редагувати інформацію;
- видаляти працівників;
- призначати посаду;
- змінювати заробітну плату;
- призначати працівників до груп або дисциплін.

Основні категорії працівників: менеджер, вихователь, помічник вихователя, викладач.

### FR-07. Керування навчальними дисциплінами

Система повинна підтримувати такі дисципліни:

1. Музика.
2. Англійська мова.
3. Фізкультура.
4. Вільна боротьба.
5. Шахи.

Для проведення кожної дисципліни повинен бути доступний відповідний викладач. Адміністратор повинен мати можливість керувати дисциплінами та призначати викладачів.

### FR-08. Формування розкладу

Система повинна забезпечувати автоматичне формування початкового розкладу занять.

Під час формування необхідно враховувати:

- вік дітей;
- групи;
- дисципліни;
- доступність викладачів;
- доступність приміщень;
- час харчування;
- час сну;
- тривалість робочого дня.

Після автоматичного формування адміністратор або викладач може коригувати розклад відповідно до своїх прав. Генерація розкладу повинна мати чіткі стани: **Draft** (створений або редагований) та **Published** (доступний для перегляду батьками й викладачами). Публікувати можна лише розклад, що пройшов перевірку конфліктів.

Для кожного елемента розкладу зберігаються дата/день, час початку і завершення, група, дисципліна, викладач і кімната. Тривалість занять і тижневе навантаження зберігаються як налаштування, а не жорстко прописуються в коді.

Зміни не повинні порушувати встановлені обмеження.

### FR-09. Рівномірність розкладу

Система повинна забезпечувати однакову кількість занять для дітей одного віку. Не допускається ситуація, коли групи одного віку мають різну кількість обов'язкових занять за однаковий розрахунковий період.

### FR-10. Режим дня

Тривалість перебування дітей у садочку становить 8 годин на день.

Протягом дня передбачено:

- сон — 60 хвилин;
- три прийоми їжі — по 30 хвилин;
- навчальні заняття;
- вільний час.

Прийоми їжі не повинні проходити підряд. Проміжки між заняттями можуть заповнюватися вільним часом.

### FR-11. Керування приміщеннями

Садочок має 20 кімнат, які перебувають у власності власника. Усі кімнати готові до використання та не потребують ремонту.

Адміністратор повинен мати можливість:

- переглядати список приміщень;
- змінювати призначення кімнати;
- закріплювати кімнату за групою;
- визначати кімнати для проведення занять;
- переглядати доступність приміщень.

Призначення кімнати:

- основне приміщення групи;
- приміщення для занять.

Кожна група повинна мати окрему основну кімнату. Система не повинна дозволяти одночасне використання одного приміщення для несумісних занять або груп.

### FR-12. Керування харчуванням

Система повинна зберігати вартість харчування залежно від віку дитини.

Початкові значення:

| Вік | Вартість за день |
|---|---:|
| 2 роки | 300 грн |
| 3 роки | 400 грн |
| 4 роки | 500 грн |
| 5 років | 600 грн |

Адміністратор повинен мати можливість змінювати вартість харчування. Харчування оплачується окремо від навчання.

### FR-13. Керування пільгами

Система повинна підтримувати такі рівні пільг: 10%, 20%, 30%.

Адміністратор повинен мати можливість:

- переглядати пільги;
- призначати пільгу дитині;
- змінювати пільгу;
- скасовувати пільгу.

Пільги застосовуються лише до вартості навчання. Пільги не застосовуються до харчування.

### FR-14. Розрахунок вартості навчання

Базова вартість навчання становить 15 000 грн на місяць за дитину.

Система повинна автоматично розраховувати:

- базову вартість;
- суму пільги;
- вартість після пільги;
- вартість харчування;
- кінцеву суму до оплати.

### FR-15. Річна оплата

Система повинна підтримувати щомісячну оплату та оплату за 12 місяців наперед. При річній оплаті застосовується додаткова знижка 12% на навчання. Харчування розраховується окремо.

### FR-16. Рахунки та платежі

Система повинна відокремлювати **Invoice** (нарахування) від **Payment** (фактично отримані кошти). Рахунок містить окремі рядки навчання, індивідуальної знижки, річної знижки та харчування, а також підсумкову суму й період.

Система повинна підтримувати:

- створення запису про оплату;
- перегляд платежів;
- прив'язку платежу до дитини;
- визначення періоду оплати;
- зберігання суми;
- зберігання дати платежу;
- перегляд історії платежів.

### FR-17. Історія змін

Система повинна передбачати збереження історії змін основних даних.

Історія повинна містити:

- ідентифікатор зміненої сутності;
- тип операції;
- дату та час;
- користувача;
- попереднє значення;
- нове значення.

Для базової версії достатньо журналу змін важливих сутностей. Повне збереження всіх історичних станів даних розглядається як розширена функціональність. Операції видалення не повинні непомітно руйнувати фінансову історію.

### FR-18. Керування фінансовими параметрами

Адміністратор повинен мати можливість змінювати:

- вартість навчання;
- вартість харчування;
- заробітні плати;
- ставки доплат;
- розрахункову вартість використання кімнат;
- інші фінансові параметри системи.

### FR-19. Розрахунок прибутку

Система повинна надавати адміністратору можливість отримати:

- дохід окремої групи;
- витрати окремої групи;
- прибуток окремої групи;
- загальний дохід садочка;
- загальні витрати садочка;
- загальний прибуток.

Розрахунок повинен враховувати оплату навчання, харчування, пільги, зарплати працівників та встановлені витрати.

Вартість харчування, сплачена батьками, повинна враховуватися як дохід, а вартість замовлення харчування — як витрата. Необхідно уникати подвійного врахування цих сум. Звіт має явно вказувати розрахунковий період та метод обліку доходу: нарахування за послуги або отримані платежі. Передоплата за рік не повинна механічно збільшувати прибуток одного місяця за всі 12 місяців у звіті за нарахуваннями.

### FR-20. Оптимізація кількості груп

Система повинна підтримувати розрахунок економічно вигідного розподілу дітей між групами.

Необхідно враховувати:

- вік дітей;
- кількість дітей;
- максимальну місткість групи;
- кількість доступних кімнат;
- зарплати вихователів;
- зарплати помічників;
- зарплати викладачів;
- пільги;
- доходи та витрати.

Метою оптимізації є максимізація прибутку з дотриманням установлених обмежень. Порівнювані сценарії мають використовувати однаковий період, однакові правила витрат і явно задану кількість дітей; оптимізація не може створювати більше місць, ніж дозволяють групи та приміщення.

### FR-21. Оптимізація приміщень

Система повинна дозволяти визначати:

- необхідну кількість кімнат;
- мінімальну окупну кількість кімнат за обраної моделі фінансових витрат;
- доцільність створення додаткової групи;
- економічно вигідне використання приміщень.

Загальна кількість одночасно використовуваних кімнат не повинна перевищувати 20.

### FR-22. Прогнозування фінансових результатів

Адміністратор повинен мати можливість задавати сценарій із певною кількістю дітей та їхнім віком.

Наприклад: «150 дітей віком 5 років».

Система повинна розраховувати:

- кількість груп;
- розподіл дітей;
- кількість необхідних кімнат;
- кількість працівників;
- витрати на персонал;
- прогнозовані доходи;
- прогнозовані витрати;
- прогнозований прибуток.

### FR-23. Доступ батьків до інформації

Батьки повинні мати можливість переглядати через API:

- власних дітей;
- їхні групи;
- розклад;
- вартість навчання;
- харчування;
- призначені пільги;
- суму до оплати.

Доступ до інформації чужих дітей заборонений.

### FR-24. Доступ викладачів до розкладу

Викладач повинен мати можливість переглядати власний розклад із зазначенням дисципліни, групи, часу та приміщення.

## 5. Бізнес-правила

### 5.1. Діти та групи

**BR-01.** До садочка приймаються діти віком від 2 до 5 років.

**BR-02.** Діти різного віку не можуть перебувати в одній групі.

**BR-03.** Максимальна кількість дітей у групі — 20.

**BR-04.** Кожна група повинна мати одного вихователя.

**BR-05.** Кожна група повинна мати одного помічника вихователя.

**BR-06.** Кожна група повинна мати окреме основне приміщення.

**BR-07.** Одна сім'я може мати декількох дітей у садочку.

### 5.2. Приміщення

**BR-08.** Загальна кількість кімнат — 20.

**BR-09.** Кімнати належать власнику садочка.

**BR-10.** Кімнати повністю готові до використання.

**BR-11.** Кімната може бути призначена для групи або проведення занять.

**BR-12.** Кількість використовуваних кімнат не може перевищувати кількість доступних.

**BR-13.** Кожна група повинна мати окрему кімнату.

### 5.3. Навчання та харчування

**BR-14.** Базова вартість навчання — 15 000 грн на місяць.

**BR-15.** Харчування оплачується окремо.

**BR-16.** Вартість харчування для дворічної дитини — 300 грн на день.

**BR-17.** Для кожного наступного року віку вартість харчування збільшується на 100 грн за день.

**BR-18.** Адміністратор може змінювати вартість харчування.

**BR-19.** Пільги застосовуються лише до навчання.

### 5.4. Пільги та оплата

**BR-20.** Доступні рівні пільг — 10%, 20%, 30%.

**BR-21.** Пільги призначає адміністратор.

**BR-22.** Оплата може здійснюватися щомісячно або за рік наперед.

**BR-23.** Річна оплата передбачає знижку 12%.

**BR-24.** Спеціальна знижка за наявність декількох дітей в одній сім'ї не передбачена.

### 5.5. Працівники

**BR-25.** Заробітна плата менеджера — 80 000 грн на місяць.

**BR-26.** Заробітна плата викладача дисципліни — 40 000 грн на місяць.

**BR-27.** Базова зарплата помічника вихователя — 20 000 грн на місяць.

**BR-28.** Зарплата вихователя розраховується за ставкою 2 000 грн за кожну дитину в групі.

**BR-29.** За кожну дитину понад 12 вихователь додатково отримує 5 000 грн.

**BR-30.** За кожну дитину понад 12 помічник додатково отримує 3 000 грн.

**BR-31.** Адміністратор може змінювати заробітні плати та ставки доплат.

### 5.6. Розклад

**BR-32.** Діти перебувають у садочку 8 годин на день.

**BR-33.** Сон триває 60 хвилин.

**BR-34.** Протягом дня передбачено три прийоми їжі по 30 хвилин.

**BR-35.** Прийоми їжі не можуть проходити підряд.

**BR-36.** Один викладач не може одночасно працювати з двома групами.

**BR-37.** Одна група не може одночасно відвідувати два заняття.

**BR-38.** Діти одного віку повинні отримувати однакову кількість занять.

## 6. Фінансові розрахунки

### 6.1. Вартість навчання

Базова місячна вартість:

`Tuition = 15000`

Вартість із пільгою:

`DiscountedTuition = Tuition × (1 - DiscountRate)`

Приклад для пільги 20%:

`15000 × 0.8 = 12000 грн`

### 6.2. Вартість харчування

Денна вартість:

`DailyMealCost = 300 + (Age - 2) × 100`

Вартість за розрахунковий період:

`MealCost = DailyMealCost × MealDays`

Кількість оплачуваних днів харчування задається відповідно до параметрів розрахункового періоду.

### 6.3. Місячна оплата

`MonthlyPayment = DiscountedTuition + MealCost`

Наприклад, для дитини 3 років із пільгою 20% та 20 оплачуваними днями харчування:

- навчання — 12 000 грн;
- харчування — 400 × 20 = 8 000 грн;
- загальна сума — 20 000 грн.

### 6.4. Річна оплата

Розрахункова формула для навчання із послідовним застосуванням знижок:

`AnnualTuition = DiscountedTuition × 12 × 0.88`

Харчування розраховується окремо за кількістю оплачуваних днів.

### 6.5. Зарплата вихователя

Формула на основі останніх зазначених замовником ставок:

`EducatorSalary = 2000 × ChildrenCount + 5000 × max(0, ChildrenCount - 12)`

### 6.6. Зарплата помічника

`AssistantSalary = 20000 + 3000 × max(0, ChildrenCount - 12)`

### 6.7. Прибуток садочка

`Profit = TotalRevenue - TotalExpenses`

Доходи включають оплату навчання та харчування.

Витрати включають:

- зарплати вихователів;
- зарплати помічників;
- зарплати викладачів;
- зарплату менеджера;
- витрати на замовлення харчування;
- інші фактичні операційні витрати, внесені в систему.

Розрахункова вартість використання власних кімнат відображається окремо від фактичних витрат. Для прозорості система може показувати два показники: **операційний прибуток** без умовної оренди та **модельний прибуток** з урахуванням нормативної вартості зайнятих кімнат. Ці показники не можна змішувати.

Умова беззбитковості для обраної моделі: `Profit >= 0`. Якщо жодна допустима конфігурація не є беззбитковою, система повинна повернути цей результат, а не вигадувати рішення.

## 10. Рекомендована структура backend

З урахуванням обраного командою стеку (Node.js, Express, PostgreSQL) доцільно розділити застосунок на логічні модулі. Це рекомендація щодо реалізації, а не окремі бізнес-вимоги:

- `auth`, `users`, `roles` — автентифікація та доступ;
- `children`, `parents`, `relatives` — діти й родинні зв'язки;
- `groups`, `rooms`, `employees` — групи, приміщення та персонал;
- `subjects`, `schedule` — дисципліни, заняття й розклад;
- `pricing`, `discounts`, `meals` — тарифи й правила оплати;
- `invoices`, `payments` — нарахування та отримання коштів;
- `expenses`, `reports`, `profit` — витрати, звіти та прибуток;
- `settings`, `audit` — змінні параметри й історія змін.

Для API рекомендовані окремі маршрути ресурсів (`/children`, `/groups`, `/rooms` тощо) та контроль доступу на кожному маршруті. Схема БД і перелік endpoint-ів формуються командою під час технічного проєктування.

## 3. Поточний стан проєкту

На завершальному етапі третього циклу команда має сформовану структуру PostgreSQL, механізм міграцій, валідатори вхідних даних, налаштовану інфраструктуру автоматичних перевірок і основу серверної частини на Express.

Водночас розробка основної функціональності триває.

Поточний стан за основними напрямами:

- **База даних:** наявна структура бізнес-таблиць і механізм міграцій; продовжується розробка та перевірка SQL-бізнес-логіки.
- **Сервісний шар:** триває реалізація взаємодії між контролерами, сервісами та SQL-функціями.
- **API:** опрацьовуються маршрути основних сутностей; необхідно завершити перевірку повного циклу запитів і відповідей.
- **Валідація:** наявні Zod-валідатори; продовжується їх інтеграція з маршрутами та перевірка поведінки на некоректних даних.
- **Тестування:** розширено покриття SQL-бізнес-логіки та перевірок API; потрібні додаткові наскрізні інтеграційні тести.
- **GitHub Actions:** автоматизовані перевірки є частиною процесу розробки; проходження всіх актуальних перевірок потрібно підтвердити результатами CI для відповідних змін.

Таким чином, проєкт перебуває на етапі інтеграції серверної архітектури та поступового переходу до повноцінного API.

## 4. Виявлені проблеми та ризики

У процесі розробки та тестування визначено такі питання, які необхідно врахувати надалі:

1. **Інтеграція сервісів із SQL-функціями.** Необхідно перевірити відповідність параметрів сервісів, контролерів і SQL-функцій, а також правильність обробки результатів запитів до PostgreSQL.

2. **Завершення API-маршрутів.** Наявність маршрутів і контролерів ще не гарантує повноцінної роботи CRUD-операцій. Потрібно перевірити створення, отримання, оновлення та видалення записів для відповідних сутностей.

3. **Валідація та узгодженість даних.** Необхідно забезпечити однакові правила перевірки на рівні Zod, серверної логіки та PostgreSQL, зокрема для обов'язкових полів, зовнішніх ключів і бізнес-обмежень.

4. **Інтеграційне тестування.** Потрібно доповнити тести перевірками успішних операцій, негативних сценаріїв, помилок бази даних і коректності HTTP-статусів.

5. **Стабільність інтеграції через GitHub.** Після об'єднання змін необхідно перевіряти сумісність компонентів, актуальність залежностей і проходження CI.

6. **Документація.** Після завершення основних API-маршрутів потрібно оновити інструкції запуску, приклади запитів і документацію щодо тестування.
